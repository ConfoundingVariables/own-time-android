### SDK levels

* Use **compileSdk/targetSdk 36** for a phone release today. Since **2026-08-31**, Google Play requires new phone apps and updates to target Android 16 / API 36; existing apps need API 35 to remain discoverable to users on newer OS versions. An extension to 2026-11-01 is available, but is irrelevant to a new app ([Play Console Help](https://support.google.com/googleplay/android-developer/answer/11926878)). A later Wear app has a different 2026 submission floor: API 35 ([same source](https://support.google.com/googleplay/android-developer/answer/11926878)).
* Recommend **minSdk 26**. This is a product/support choice, not a Compose requirement: current AndroidX is moving many libraries from minSdk 23 to 24 from July 2026 ([AndroidX release channels](https://developer.android.com/jetpack/androidx/versions/all-channel)); Quick Settings `TileService` begins at API 24 ([TileService reference](https://developer.android.com/reference/kotlin/android/service/quicksettings/TileService)); API 26 gives native notification channels ([notification channels guide](https://developer.android.com/develop/ui/views/notifications/channels)). Runtime notification permission still needs an API 33 path ([notification permission guide](https://developer.android.com/develop/ui/views/notifications/notification-permission)).
* A day-budget reset does **not** inherently justify exact alarms: Android says exact alarms should be used only when a user-facing function requires precise timing, and Android 12+ exact alarms involve `SCHEDULE_EXACT_ALARM` user access or the policy-constrained `USE_EXACT_ALARM` permission ([alarm guidance](https://developer.android.com/develop/background-work/services/alarms)). Model reset lazily from the local date whenever state is read; use an alarm only for an explicitly promised midnight notification.
* Google does not publish a stable public API-level install-share table suitable for a durable minSdk calculation; the distribution shown by Android Studio's New Project wizard changes with its live dataset. Therefore this research could not cite a defensible public percentage for API 26. Re-check the wizard immediately before locking minSdk.

## 2. Storage comparison

### The export invariant

The requested export must be a **single, consistent SQLite snapshot**, not a filesystem copy of an open WAL database. In WAL mode, committed data may be in the `-wal` file; SQLite says the WAL is part of the database's persistent state and separating it from the main file can lose transactions or corrupt the database ([WAL documentation](https://sqlite.org/wal.html)). The SQLite Online Backup API produces a destination snapshot while permitting concurrent access ([Backup API](https://sqlite.org/backup.html)); `VACUUM INTO` is the official alternative that creates a compact, consistent new database file from a live database ([VACUUM](https://sqlite.org/lang_vacuum.html)). A checkpoint merely transfers WAL content into the main file and can be blocked by readers; it is not by itself an atomic export protocol ([WAL checkpointing](https://sqlite.org/wal.html#ckpt)).

Accordingly, preferred export order is: (1) briefly serialize app writes, (2) create a temporary snapshot with `VACUUM INTO` or a surfaced backup API, (3) close the snapshot, (4) expose it with `FileProvider` and `ACTION_SEND`, and (5) delete it later. Android requires secure `content://` sharing with temporary URI permission rather than `file://` URIs ([secure file sharing](https://developer.android.com/training/secure-file-sharing/share-file)). A raw copy of only the live `.db` file is unacceptable. A deliberate checkpoint followed by copying while **all connections are closed and remain closed** can work, but is more interruption-prone than asking SQLite to make the snapshot.

### Event-log shape

Use one immutable row per fact: `event_id`, `device_id`, `device_seq`, `wall_time`, optional monotonic/context time, `kind`, `entity_id`, payload/version, and `created_at`; unique `(device_id, device_seq)` and unique `event_id` make import idempotent. Treat corrections as new events (adjust, supersede, tombstone), not updates. Keep rebuildable projection tables for priorities, today's totals, active timer and history summaries; append event plus update projection in one SQLite transaction. SQLite transactions are atomic even across crashes ([transaction documentation](https://sqlite.org/lang_transaction.html)). The raw event history remains authoritative; projection schema can evolve and be rebuilt.

## 3. Wear OS peer-to-peer sync

The Wearable Data Layer is part of **Google Play services**, works between Wear OS watches and paired Android devices, and may route over Bluetooth or—when unavailable—through Google-owned cloud relay infrastructure ([Data Layer overview](https://developer.android.com/training/wearables/data/overview)). Thus “no app server” is accurate, but “bytes never transit cloud infrastructure” is not guaranteed. It does not work for a Wear watch paired to iOS ([sync guide](https://developer.android.com/training/wearables/data/sync)). Matching applications must use the same package name and signing certificate for production communication ([packaging guidance](https://developer.android.com/training/wearables/apps/packaging)). Devices without Google Play services cannot use this API ([Data Layer overview](https://developer.android.com/training/wearables/data/overview)).

### Clients and guarantees

* **`DataClient`** replicates persistent `DataItem`s to all nodes; writes can occur offline and synchronize when nodes reconnect. Items persist until deleted, but Google explicitly says Data Layer is synchronization—not app storage—so each peer must persist its own copy ([sync guide](https://developer.android.com/training/wearables/data/sync)). Normal items should be small; use `Asset` for large blobs. The comparison table says DataClient supports over 100 KB through Assets and works offline ([client types](https://developer.android.com/training/wearables/data/client-types)). Concurrent writes to the same item can be inconsistent, so Google recommends creator-owned items or immutable producer/consumer items with unique IDs ([DataClient reference](https://developers.google.com/android/reference/com/google/android/gms/wearable/DataClient)).
* **`MessageClient`** is connected-node, ephemeral RPC/command transport: no persistence and no retry. Success means queued, **not delivered**; payloads should generally be no larger than **100 KB** ([MessageClient reference](https://developers.google.com/android/reference/com/google/android/gms/wearable/MessageClient), [client comparison](https://developer.android.com/training/wearables/data/client-types)). Never use a message as the only record of timer state.
* **`ChannelClient`** is a bidirectional byte stream for connected nodes and large files/streams. It has no offline persistence or automatic synchronization; the application owns framing, retry and consistency ([client types](https://developer.android.com/training/wearables/data/client-types), [ChannelClient reference](https://developers.google.com/android/reference/com/google/android/gms/wearable/ChannelClient)). It is useful for bulk bootstrap/export, not the canonical event queue.
* The official references do not promise cross-item/message global ordering or exactly-once delivery. Therefore treat all received batches as duplicated, delayed and reorderable; acknowledge progress in application data rather than inferring it from callback order.

### Protocol consequence

Give every installation a durable random `device_id` and allocate a strictly increasing `device_seq` transactionally with each local event. Exchange immutable batches/ranges, merge by `event_id` or `(device_id, device_seq)`, and track each peer's highest **contiguous** sequence plus holes. `wall_time` is useful for display but cannot establish causality because clocks skew; sequence orders one device only. Use DataItems owned by their creator (for example, per-device manifest/high-water mark and immutable chunks); use MessageClient only to nudge a connected peer, and periodically reconcile manifests so dropped nudges do not matter. This follows Google's ownership guidance for avoiding concurrent DataItem updates ([DataClient reference](https://developers.google.com/android/reference/com/google/android/gms/wearable/DataClient)).

Conflicts need product rules before watch work:

* **Simultaneous timer starts:** both are valid facts but violate “one timer.” Pick a deterministic winner (causal predecessor if known; otherwise a documented tie-break such as `(wall_time, device_id, seq)`) and generate/display a repair adjustment for overlap.
* **Edit vs delete:** represent both as events referring to immutable IDs. Define tombstone-wins, edit-wins, or surface conflict; never overwrite the original event. Tombstone-wins is simplest but can hide a later intentional restoration, so restoration needs its own event.
* **Budget/priority edits on both peers:** use field-level last-writer rules only if clock skew is acceptable; otherwise serialize through an explicit revision/parent and surface divergent revisions. Set-like entities can use stable IDs plus tombstones.
* **Reset:** midnight should be a derived boundary in the user's selected zone, not a destructive synchronized “clear.” Store instants plus relevant zone/date semantics, because peers can cross midnight or change zones at different times.

## 4. Other baselines

### Dependency injection

Android explicitly calls **Hilt** Jetpack's recommended DI library and notes compile-time correctness, lifecycle containers and Android Studio support ([DI guide](https://developer.android.com/training/dependency-injection)). Hilt's current setup example uses Dagger/Hilt **2.57.1** ([Hilt guide](https://developer.android.com/training/dependency-injection/hilt-android)). For this small v1, manual constructor injection plus one application container is also defensible and minimizes generated machinery; Android recommends Hilt over manual DI “when possible” ([manual DI guide](https://developer.android.com/training/dependency-injection/manual)). Koin is a third-party service-locator/DI option with KMP support ([Koin official docs](https://insert-koin.io/docs/setup/why-koin/)); it is not Android's official recommendation. Choose Hilt if the graph will span phone, services, workers and later Wear; choose manual DI if keeping v1 very small. Do not choose Koin merely to avoid a small manual graph.

### Navigation

Classic **Navigation Compose 2.10.2** is stable ([Navigation releases](https://developer.android.com/jetpack/androidx/releases/navigation)). **Navigation 3 is no longer preview**: 1.0 became stable and current stable is **1.2.0**; it is Compose-first and makes application-owned back-stack state central ([Navigation 3 releases](https://developer.android.com/jetpack/androidx/releases/navigation3)). For a new Compose-only app, Navigation 3 is reasonable; Navigation Compose remains the lower-migration-risk choice because it has longer production history and richer established integrations. This is a human trade-off, not a stability blocker.

### Widgets and quick controls

Glance supplies a Compose-style API for remote surfaces; current stable **1.2.0** supports app widgets ([Glance releases](https://developer.android.com/jetpack/androidx/releases/glance)). It is suitable for a later home-screen widget, but Glance composables are translated to `RemoteViews` and are not ordinary Compose UI ([Glance app-widget guide](https://developer.android.com/develop/ui/compose/glance)). For phone Quick Settings, platform `TileService` exists from API 24 and tiles are user-added services with a distinct binding lifecycle ([TileService reference](https://developer.android.com/reference/kotlin/android/service/quicksettings/TileService)). A tile should issue an idempotent command into the same repository/event writer, not own timer state.

### Assistant / shortcuts

**App Actions are still supported, not deprecated**, as of the official Assistant documentation updated in July 2026. They map `<capability>` declarations in `shortcuts.xml` to built-in intents and launch destinations; they support Android 5+ phones, require Play publication/review, and can use static/dynamic shortcuts ([Assistant overview](https://developer.android.com/develop/devices/assistant/overview), [build guide](https://developer.android.com/develop/devices/assistant/get-started)). Ordinary Android static/dynamic shortcuts remain useful independently of Assistant ([shortcuts overview](https://developer.android.com/develop/ui/views/launch/shortcuts)). For v1, implement launcher shortcuts/deep links first; add App Actions only if an available built-in intent maps cleanly to “start/switch priority,” because Assistant availability and review are external dependencies. There is no official source indicating a replacement or deprecation.

## 5. Recommendation

1. Start with Kotlin **2.4.20**, AGP **9.4.0**, Gradle **9.6.0**, JDK 17, compile/target 36, min 26, Compose BOM **2026.09.00**, stable Material3 **1.4.0** and stable Adaptive **1.3.0**. Avoid Material3 1.5 alpha/Expressive in the v1 critical path ([version sources above](https://developer.android.com/jetpack/androidx/releases/compose-material3)).
2. Choose **Room 2.8.5** for the lowest-risk Android-first release, with immutable events plus transactional, rebuildable projections. Put storage behind domain interfaces so a later shared core is possible. Room already has KMP support, but do not make KMP modularity a v1 prerequisite ([Room KMP guide](https://developer.android.com/kotlin/multiplatform/room)). Evaluate Room3 separately before adoption because its stable API is newer ([Room3 releases](https://developer.android.com/jetpack/androidx/releases/room3)).
3. Prototype the exact export path early on the minimum and target OS versions. Prefer `VACUUM INTO` to a temporary file, validate with `PRAGMA integrity_check`, then share through `FileProvider`; never share/copy the open live WAL database ([SQLite VACUUM](https://sqlite.org/lang_vacuum.html), [integrity check](https://sqlite.org/pragma.html#pragma_integrity_check)). If the selected Room/driver combination cannot execute `VACUUM INTO` reliably on every supported API, serialize writes, close Room, copy the checkpointed main file, reopen, and test crash/cancellation paths.
4. Use manual DI initially if the app stays a handful of repositories/use cases; otherwise use Hilt, Android's recommended option ([DI guide](https://developer.android.com/training/dependency-injection)). Use Navigation 3 for a new Compose-only UI if application-owned navigation state is desired; otherwise Navigation Compose 2.10.2 is conservative.
5. Design event identity and merge semantics now even though Wear is later: durable device ID, per-device sequence, immutable correction/tombstone events, idempotent imports, and deterministic conflict policies. Data Layer then transports/reconciles facts rather than becoming the database.

### Human decisions still required

* **minSdk 26 vs 24:** 26 simplifies notification behavior and remains sensible; 24 extends reach and still supports tiles. Public current device-share percentages could not be verified.
* **Room 2 vs Room3 vs SQLDelight:** Room 2 minimizes Android delivery risk; Room3 maximizes current Jetpack KMP direction but is newer; SQLDelight maximizes explicit SQL and cross-platform flexibility at the cost of non-Google tooling and somewhat more plumbing.
* **Export implementation:** `VACUUM INTO` simplicity versus a native/driver backup API, and whether a brief write pause is acceptable.
* **Navigation 3 vs Navigation Compose:** newer state-owned model versus longer operational history.
* **Conflict UX:** deterministic silent resolution versus showing overlap/edit conflicts to the user.

## Facts not verified from primary sources

* No public, current Google API-level device-share percentages were found; Android Studio's live wizard should be consulted at project creation.
* Data Layer documentation does not state a formal ordering guarantee. This document therefore deliberately assumes none; it does not claim callbacks are reordered in every implementation.
* No Android/Room API documents a universal one-call live-database export. The chosen `VACUUM INTO` path must be proven against the actual Android SQLite/AndroidX bundled driver and supported API range in a spike.
