# Android alarm and notification rules for a daily-budget timer

**Research date:** 2026-10-01. **Scope:** current Android/Google Play rules relevant to a free, offline, user-started countdown timer. Sources are first-party Android, AOSP, or Google Play documentation. Policy approval is ultimately a Google Play review decision.

## Executive conclusion

The product is genuinely timer-like: its core user-facing function starts a countdown and alerts at expiry. Google Play explicitly lists an **alarm or timer app** as an acceptable `USE_EXACT_ALARM` use case, so there is a defensible route to automatic exact-alarm access. It is not risk-free: the store reviews the declaration, and “daily priorities/time budgeting” may be read as productivity rather than a dedicated timer. `SCHEDULE_EXACT_ALARM` is the lower-rejection fallback, but on fresh installs it requires the user to grant special access before the exact promise can be made. [Play exact-alarm policy](https://support.google.com/googleplay/android-developer/answer/16909972?hl=en) [Android alarm guidance](https://developer.android.com/develop/background-work/services/alarms)

No Android API can unconditionally promise “gets through DND/silent mode.” Correct alarm audio semantics (`USAGE_ALARM`, `CATEGORY_ALARM`) let the alert participate in the user's alarm/DND policy; the user can still disallow alarms, block or silence the notification channel, deny notifications, revoke full-screen access, or use a DND mode that mutes alarms. [Android notification/DND guide](https://developer.android.com/develop/ui/compose/notifications) [ZenPolicy API](https://developer.android.com/reference/android/service/notification/ZenPolicy.Builder#allowAlarms(boolean))

## 1. Exact alarms

### Permissions and default state

* Exact-alarm calls require either `SCHEDULE_EXACT_ALARM` or `USE_EXACT_ALARM` for apps targeting Android 12/API 31 or later; the affected `PendingIntent` APIs include `setExact()`, `setExactAndAllowWhileIdle()`, and `setAlarmClock()`. An `OnAlarmListener` exact alarm is permission-exempt, but only works while the app process remains alive and therefore is not suitable for the durable expiry guarantee. [Android exact-alarm guide](https://developer.android.com/develop/background-work/services/alarms) [Android 14 exact-alarm change](https://developer.android.com/about/versions/14/changes/schedule-exact-alarms)
* `USE_EXACT_ALARM` was added in API 33, is a normal install-time permission, is automatically granted, and cannot be revoked by the user. It is intended only where exact alarms are core functionality and is audited by app stores. [Manifest permission reference](https://developer.android.com/reference/android/Manifest.permission#USE_EXACT_ALARM) [Android exact-alarm guide](https://developer.android.com/develop/background-work/services/alarms)
* `SCHEDULE_EXACT_ALARM` is user-granted special app access and can be revoked by the user or system. Android 12/12L introduced this access. On Android 13, fresh installs targeting API 33+ are not pre-granted; Android 14 makes denial-by-default explicit for most fresh installs targeting API 33+, including backup/restore to Android 14. Existing granted apps retain it across an OS upgrade to Android 14. Apps targeting below API 31 can schedule exact alarms, but that target is not viable for current Play submission. [Android exact-alarm guide](https://developer.android.com/develop/background-work/services/alarms) [Android 14 exact-alarm change](https://developer.android.com/about/versions/14/changes/schedule-exact-alarms) [AlarmManager reference](https://developer.android.com/reference/android/app/AlarmManager#canScheduleExactAlarms())
* Therefore, check `AlarmManager.canScheduleExactAlarms()` immediately before scheduling. If false, explain the feature and open `Settings.ACTION_REQUEST_SCHEDULE_EXACT_ALARM`; re-check on return. The grant broadcast is `AlarmManager.ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED`. [Special-permission guide](https://developer.android.com/training/permissions/requesting-special) [Android exact-alarm guide](https://developer.android.com/develop/background-work/services/alarms)

### Does this app qualify for `USE_EXACT_ALARM`?

Google Play limits `USE_EXACT_ALARM` to core, user-facing functionality requiring precisely timed actions and gives two acceptable examples: **an alarm or timer app**, and a calendar app showing event notifications. This product's user-started budget countdown and expiry alarm fit “timer app” in substance, more strongly than a generic productivity reminder. The declaration should show that starting and expiring one active timer is the central experience—not an incidental reminder feature. Nevertheless, approval cannot be guaranteed; use `SCHEDULE_EXACT_ALARM` if Play decides that time budgeting is not a qualifying dedicated alarm/timer use case. [Google Play exact-alarm policy](https://support.google.com/googleplay/android-developer/answer/16909972?hl=en)

### `setAlarmClock()` versus `setExactAndAllowWhileIdle()`

* `setAlarmClock(AlarmClockInfo, operation)` is the strongest alarm-clock semantic: it is precise, always `RTC_WAKEUP`, highly visible to the user, may cause the system to show an upcoming-alarm indicator, and the system exits low-power modes shortly before delivery. It should be reserved for alarm-clock-like events. [Alarm scheduling guide](https://developer.android.com/develop/background-work/services/alarms) [Doze guide](https://developer.android.com/training/monitoring-device-state/doze-standby) [AlarmManager reference](https://developer.android.com/reference/android/app/AlarmManager#setAlarmClock(android.app.AlarmManager.AlarmClockInfo,%20android.app.PendingIntent))
* `setExactAndAllowWhileIdle()` is an exact, idle-capable one-shot alarm and is the less misleading semantic for an elapsed user-started timer. It receives a temporary power exemption at dispatch, but idle-capable alarms are rate-limited and Android may give their ordering/scheduling more flexibility; official references describe delivery as nearly/as close as possible, not hard real-time. [AlarmManager reference](https://developer.android.com/reference/android/app/AlarmManager#setExactAndAllowWhileIdle(int,%20long,%20android.app.PendingIntent))
* Recommendation: use a one-shot `ELAPSED_REALTIME_WAKEUP` `setExactAndAllowWhileIdle()` for the active budget's monotonic deadline. Consider `setAlarmClock()` only if product presentation and Play declarations honestly position every expiry as a user-configured alarm and the visible upcoming-alarm affordance is acceptable. Neither API overrides missing exact-alarm access. [AlarmManager reference](https://developer.android.com/reference/android/app/AlarmManager) [Android exact-alarm guide](https://developer.android.com/develop/background-work/services/alarms)

### Doze, App Standby, revocation, and reconstruction

Ordinary alarms are deferred in Doze. `setExactAndAllowWhileIdle()` can fire in Doze, while `setAlarmClock()` continues normally and wakes the device out of Doze shortly beforehand. App Standby mainly defers background network/jobs; exact user alarms remain the appropriate primitive. Android still does not offer a literal hard-real-time guarantee, and force-stop prevents app alarms/components until the user launches the app again. [Doze/App Standby guide](https://developer.android.com/training/monitoring-device-state/doze-standby) [Alarm scheduling guide](https://developer.android.com/develop/background-work/services/alarms)

If `SCHEDULE_EXACT_ALARM` is revoked, the app process is stopped and all future exact alarms created by `setExact`, `setExactAndAllowWhileIdle`, and `setAlarmClock` are deleted. There is a broadcast on **grant**, not a dependable revocation callback; always persist timer state, check access before scheduling, and reconstruct alarms after a later grant/app start. [Android exact-alarm guide](https://developer.android.com/develop/background-work/services/alarms) [AlarmManager reference](https://developer.android.com/reference/android/app/AlarmManager#ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED)

All alarms are cleared on reboot. Persist enough state to decide whether an active session should resume or immediately expire, request `RECEIVE_BOOT_COMPLETED`, and reschedule from a manifest receiver for `BOOT_COMPLETED` (only enable that receiver while needed). [Alarm scheduling guide](https://developer.android.com/develop/background-work/services/alarms#boot)

For a duration timer, use `elapsedRealtime`/`ELAPSED_REALTIME_WAKEUP`; manual wall-clock or time-zone changes should not change remaining duration. `elapsedRealtime` resets at boot, so persist both remaining/session state and a wall-clock checkpoint for recovery policy. `TIME_SET` and `TIMEZONE_CHANGED` matter only for wall-clock-derived events such as “daily reset at local midnight” or if an RTC alarm is used; receive them and recompute those schedules. The platform defines these protected system broadcasts as `Intent.ACTION_TIME_CHANGED` (`TIME_SET`) and `Intent.ACTION_TIMEZONE_CHANGED`. [Intent reference: TIME_CHANGED](https://developer.android.com/reference/android/content/Intent#ACTION_TIME_CHANGED) [Intent reference: TIMEZONE_CHANGED](https://developer.android.com/reference/android/content/Intent#ACTION_TIMEZONE_CHANGED) [AlarmManager clock bases](https://developer.android.com/reference/android/app/AlarmManager)

## 2. Full-screen intents

Declare `USE_FULL_SCREEN_INTENT` and place a full-screen `PendingIntent` on the high-importance alarm notification. Full-screen intents are intended for extremely urgent alarms and incoming calls; while the device is in active use, System UI normally shows a heads-up notification rather than taking over the screen. [Time-sensitive notifications guide](https://developer.android.com/develop/ui/views/notifications/time-sensitive) [Android 14 behavior changes](https://developer.android.com/about/versions/14/behavior-changes-14#secure-fsi)

Since Android 14/API 34, automatic full-screen access is restricted to apps providing calling or alarm functionality. For Play-distributed apps targeting API 34+, Google Play enables it by default only for approved calling/alarm apps (policy effective for this flow from 2025-01-22); other apps must ask the user in special access settings and gracefully degrade. The Play Console full-screen declaration has been required since 2024-05-31. [Play Console requirements](https://support.google.com/googleplay/android-developer/answer/13392821?hl=en) [AOSP FSI limits](https://source.android.com/docs/core/permissions/fsi-limits)

On API 34+, test `NotificationManager.canUseFullScreenIntent()`. If false, explain and open `Settings.ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT`. A denied FSI becomes an expanded/persistent heads-up treatment rather than a launched full-screen activity; AOSP's test matrix documents a 60-second heads-up display in denied cases. The user can revoke access even for a qualifying app. [NotificationManager reference](https://developer.android.com/reference/android/app/NotificationManager#canUseFullScreenIntent()) [AOSP FSI limits](https://source.android.com/docs/core/permissions/fsi-limits)

This product can plausibly declare alarm functionality, but its automatic grant and exact full-screen behavior must not be represented as guaranteed until Play approves the declaration and runtime checks pass.

## 3. Alarm sound, silent mode, DND, and wrap-up alerts

Create a dedicated, user-visible **budget alarms** channel at `IMPORTANCE_HIGH`, configure its sound with `AudioAttributes.USAGE_ALARM` (and an appropriate alarm content type), and post expiry notifications with `Notification.CATEGORY_ALARM`. `CATEGORY_ALARM` expressly covers alarms or timers; importance/category/audio attributes help Android route, rank, and filter correctly. Users retain final control of channel sound and importance after channel creation. [Notification categories/design](https://developer.android.com/design/ui/mobile/guides/home-screen/notifications#predefined-categories) [AudioAttributes reference](https://developer.android.com/reference/android/media/AudioAttributes#USAGE_ALARM) [Channel guide](https://developer.android.com/develop/ui/compose/notifications/channels)

These fields do **not** mean unconditional DND bypass. DND can be “alarms only,” can allow alarms in priority mode, or can use a total-silence/policy configuration that blocks alarms. `ZenPolicy.allowAlarms(false)` mutes the alarm stream; visual effects including full-screen intents can also be suppressed. A channel bypass applies only when its `canBypassDnd()` state and the active DND policy permit priority channels. Do not request notification-policy access merely to defeat the user's DND choice. [Notification/DND guide](https://developer.android.com/develop/ui/compose/notifications) [ZenPolicy `allowAlarms`](https://developer.android.com/reference/android/service/notification/ZenPolicy.Builder#allowAlarms(boolean)) [NotificationChannel `canBypassDnd`](https://developer.android.com/reference/android/app/NotificationChannel#canBypassDnd())

Silent/ringer mode and alarm volume are distinct system controls, so `USAGE_ALARM` is the correct route for an alarm that should sound while the ringer is silent; however, zero alarm volume, channel muting, DND policy, OEM behavior, and user settings still win. [AudioAttributes reference](https://developer.android.com/reference/android/media/AudioAttributes#USAGE_ALARM) [Notification/DND guide](https://developer.android.com/develop/ui/compose/notifications)

Put optional wrap-up alerts on a separate **wrap-up reminders** channel. Use high importance only if the warning truly warrants heads-up interruption; otherwise default importance is more proportionate. Do not use alarm audio, `CATEGORY_ALARM`, exact scheduling, or FSI merely to inflate a pre-alert. High importance makes sound and may peek, but channel settings and DND decide the result. [Notification importance guidance](https://developer.android.com/design/ui/mobile/guides/home-screen/notifications#settings) [Time-sensitive notification guide](https://developer.android.com/develop/ui/views/notifications/time-sensitive)

## 4. `POST_NOTIFICATIONS` (Android 13+)

`POST_NOTIFICATIONS` is a runtime permission on API 33+. Fresh installs start with notifications off; if denied, all ordinary channels are blocked. Alarm notifications are **not** among the documented exemptions (only media-session notifications and qualifying self-managed-call notifications are), so exact delivery of a broadcast does not make its alarm notification, sound, or FSI visible. Request the permission contextually before allowing the user to rely on alarms, and verify `areNotificationsEnabled()` plus alarm-channel state. [Notification permission guide](https://developer.android.com/develop/ui/views/notifications/notification-permission)

An app may start a foreground service without `POST_NOTIFICATIONS`, and must still supply its foreground notification, but after denial the user sees the FGS notice only in Task Manager, not the notification drawer. Thus a foreground service is not a workaround for denied notifications and cannot deliver the promised ongoing UI or alarm alert. [Notification permission guide](https://developer.android.com/develop/ui/views/notifications/notification-permission#exemptions)

The app should refuse or clearly label a “silent/in-app-only” degraded session when notification permission, the alarm channel, exact-alarm access, or required FSI access is absent; it must not claim the real-alarm guarantee.

## 5. Ongoing session display and foreground services

### Plain notification

A posted ongoing notification can render a system-updated countdown without per-second app work: set the deadline as `when`, call `setUsesChronometer(true)`, and `setChronometerCountDown(true)` (countdown added in API 24). Add a Stop `PendingIntent`, mark it ongoing, and update only on semantic changes. This display is cosmetic; the durable expiry remains the AlarmManager alarm. [Notification.Builder `setUsesChronometer`](https://developer.android.com/reference/android/app/Notification.Builder#setUsesChronometer(boolean)) [Notification.Builder `setChronometerCountDown`](https://developer.android.com/reference/android/app/Notification.Builder#setChronometerCountDown(boolean))

A notification alone does not keep the process alive. That is acceptable if no continuous computation is needed: persist start/deadline, derive remaining time from monotonic time whenever rendered, and let AlarmManager wake a receiver at expiry. This is safer than inventing an FGS solely to keep a countdown ticking. [Alarm scheduling guide](https://developer.android.com/develop/background-work/services/alarms) [Process lifecycle](https://developer.android.com/guide/components/activities/process-lifecycle)

### Foreground service assessment

Android 14+ requires every FGS to declare a matching type and permission. None of the standard types describes “wait while a local countdown elapses.” `shortService` lasts only about three minutes and is unsuitable for arbitrary daily-budget sessions. `dataSync`, media, health, or location would be false declarations. The only conceivable type is `specialUse`, with `FOREGROUND_SERVICE_SPECIAL_USE` and a free-form manifest property, but both platform and Play review whether it is a valid, user-perceptible use not covered elsewhere. [Android 14 FGS types](https://developer.android.com/about/versions/14/changes/fgs-types-required) [FGS type reference](https://developer.android.com/develop/background-work/services/fgs/service-types#special-use)

Google Play requires apps targeting API 34+ to declare each FGS type in Play Console, explain functionality and interruption impact, provide a demonstration video, and select/describe its use case. The timer is fully reconstructible and AlarmManager supplies expiry, so the interruption-harm argument for `specialUse` is weak. Recommendation: **do not use an FGS for v1**. If later functionality genuinely performs continuous work, submit `specialUse` transparently rather than mislabeling it. [Play FGS declaration requirements](https://support.google.com/googleplay/android-developer/answer/13392821?hl=en) [Play FGS policy](https://support.google.com/googleplay/android-developer/answer/13315670)

### Android 16 Live Updates

API 36's promoted ongoing notifications (“Live Updates”) are enhanced notification presentation, not a service or scheduling primitive. Eligibility requires an ongoing, user-initiated, time-sensitive activity that benefits from glanceable monitoring. A user-started active budget timer has a plausible fit, but official examples do not expressly list general countdown timers, and OEMs may add criteria. Treat promotion as optional enhancement, never as the alarm mechanism. [Live Updates guide](https://developer.android.com/develop/ui/views/notifications/live-update)

On API 36, a promotable notification must: use an allowed standard style (including `Notification.ProgressStyle`), declare non-runtime `POST_PROMOTED_NOTIFICATIONS`, request promoted-ongoing status, be ongoing, have a title, avoid custom `RemoteViews`, group-summary and colorized status, and use a channel above `IMPORTANCE_MIN`. Check `hasPromotableCharacteristics()` and `NotificationManager.canPostPromotedNotifications()`; the user can control promotion via `Settings.ACTION_MANAGE_APP_PROMOTED_NOTIFICATIONS`. A chronometer countdown can appear in the status chip while positive. Provide a normal ongoing notification on earlier releases or if promotion is unavailable. [Live Updates requirements](https://developer.android.com/develop/ui/views/notifications/live-update#requirements) [NotificationManager promotion API](https://developer.android.com/reference/android/app/NotificationManager#canPostPromotedNotifications())

## 6. Lock-screen visibility

Per notification, `VISIBILITY_PUBLIC` shows full content on a secure lock screen; `VISIBILITY_PRIVATE` permits a redacted public version/basic app identity; `VISIBILITY_SECRET` hides it from the secure lock screen. The user's global lock-screen settings still control final display. [Android notification design guide](https://developer.android.com/design/ui/mobile/guides/home-screen/notifications#lock-screen-notifications) [Notification visibility constants](https://developer.android.com/reference/android/app/Notification#VISIBILITY_PRIVATE)

For the per-priority “hide from lock screen” option, build that session notification with `VISIBILITY_SECRET`. If the requirement instead means “show that a timer exists but conceal priority name/remaining details,” use `VISIBILITY_PRIVATE` and `setPublicVersion()` with neutral text. Do not attempt to change channel lock-screen visibility: `NotificationChannel.setLockscreenVisibility()` is system/ranker-only in current API behavior. [Notification.Builder `setPublicVersion`](https://developer.android.com/reference/android/app/Notification.Builder#setPublicVersion(android.app.Notification)) [NotificationChannel reference](https://developer.android.com/reference/android/app/NotificationChannel#setLockscreenVisibility(int))

## 7. OEM and battery-optimization risks

Android's compatibility model specifies the APIs, but device manufacturers may add power-management behavior. Android's own guidance requires testing Doze/App Standby and documents that normal alarms/jobs/network are deferred; only the proper idle-capable/alarm-clock APIs receive the stated handling. It also notes that Google Play prohibits direct requests for battery-optimization exemption unless the app's core function is adversely affected. [Doze/App Standby guide](https://developer.android.com/training/monitoring-device-state/doze-standby)

Full-screen behavior also has OEM variance: AOSP requires Android 14 OEMs/app stores to set initial FSI grant state, and its documented fallback varies with display state. Live Update OEMs may apply additional eligibility criteria. Test representative Pixel, Samsung, Xiaomi/Oppo-family, and other target devices physically; an Android emulator cannot validate vendor power management or real lock-screen/audio behavior. [AOSP FSI limits](https://source.android.com/docs/core/permissions/fsi-limits) [Live Updates guide](https://developer.android.com/develop/ui/views/notifications/live-update#promotion-characteristics)

Do not prompt every user for `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`. If field evidence shows a supported OEM breaks the core alarm despite exact idle-capable APIs, provide device-specific troubleshooting and consider a narrowly justified exemption flow only after checking Play policy. `dontkillmyapp.com` may be useful as a **secondary, community-maintained** troubleshooting catalogue, but it is not authoritative and is intentionally not evidence for claims in this report.

## 8. Recommendation and Play-rejection risks

1. **Core scheduling:** persist the active timer; schedule one `ELAPSED_REALTIME_WAKEUP` `setExactAndAllowWhileIdle()` expiry; schedule wrap-up separately (exact only if its precision is genuinely user-critical); reconstruct after reboot/grant and derive UI from monotonic time. [Alarm scheduling guide](https://developer.android.com/develop/background-work/services/alarms)
2. **Permission strategy:** submit `USE_EXACT_ALARM` only with product/store copy and declaration demonstrating that the app is fundamentally a user-operated timer. Keep a build/product fallback to `SCHEDULE_EXACT_ALARM`, because classification as a productivity budget app is the largest exact-alarm rejection risk. Never declare both as a hedge. [Play exact-alarm policy](https://support.google.com/googleplay/android-developer/answer/16909972?hl=en) [Android exact-alarm guide](https://developer.android.com/develop/background-work/services/alarms)
3. **Expiry alert:** dedicated high-importance alarm channel, `USAGE_ALARM`, `CATEGORY_ALARM`, FSI notification, and a full-screen alarm activity only when runtime access allows it. Explain that DND/channel/user settings can prevent sound or full-screen display; do not promise unconditional bypass. [Time-sensitive notification guide](https://developer.android.com/develop/ui/views/notifications/time-sensitive) [Notification/DND guide](https://developer.android.com/develop/ui/compose/notifications)
4. **Onboarding gate:** before the first relied-upon session, contextually obtain `POST_NOTIFICATIONS`, exact-alarm special access if using `SCHEDULE_EXACT_ALARM`, and FSI special access if not auto-granted. Check all states and channel importance/sound each time the promise matters; provide explicit degraded behavior. [Notification permission guide](https://developer.android.com/develop/ui/views/notifications/notification-permission) [AOSP FSI limits](https://source.android.com/docs/core/permissions/fsi-limits)
5. **Session UI:** use a plain ongoing chronometer/countdown notification plus Stop action; no foreground service in v1. Optionally adopt API 36 Live Updates with a standard/`ProgressStyle` notification while preserving the normal path. [Notification chronometer API](https://developer.android.com/reference/android/app/Notification.Builder#setChronometerCountDown(boolean)) [Live Updates guide](https://developer.android.com/develop/ui/views/notifications/live-update)
6. **Privacy:** map “hide on lock screen” to `VISIBILITY_SECRET`; offer private/redacted as a distinct option if desired. [Lock-screen notification guide](https://developer.android.com/design/ui/mobile/guides/home-screen/notifications#lock-screen-notifications)

### Principal Play/reliability risks

* Play may reject `USE_EXACT_ALARM` or withhold default FSI access if reviewers regard time budgeting as productivity rather than core alarm/timer functionality. Use literal, demonstrable timer behavior and truthful declarations; have the user-granted path ready. [Play exact-alarm policy](https://support.google.com/googleplay/android-developer/answer/16909972?hl=en) [Play FSI requirements](https://support.google.com/googleplay/android-developer/answer/13392821?hl=en)
* A `specialUse` FGS used merely to keep a timer alive has a substantial declaration/review risk and adds no necessary expiry guarantee. [FGS special-use docs](https://developer.android.com/develop/background-work/services/fgs/service-types#special-use) [Play FGS declaration requirements](https://support.google.com/googleplay/android-developer/answer/13392821?hl=en)
* Marketing “exact” or “bypasses DND” without qualifications is technically unsafe because users control notifications, channels, FSI, DND, alarm volume, force-stop, and (for `SCHEDULE_EXACT_ALARM`) exact access. [Notification permission guide](https://developer.android.com/develop/ui/views/notifications/notification-permission) [Notification/DND guide](https://developer.android.com/develop/ui/compose/notifications)

### `minSdk` implications

The alarm architecture itself can support API 23+ (`setExactAndAllowWhileIdle` arrived in API 23); full-screen notification patterns apply from API 29+, channels require API 26+, countdown chronometer requires API 24+, exact special access begins at API 31, `POST_NOTIFICATIONS` at API 33, FSI runtime checks at API 34, and Live Updates/`ProgressStyle` at API 36. Guard each API by SDK level. [AlarmManager API](https://developer.android.com/reference/android/app/AlarmManager#setExactAndAllowWhileIdle(int,%20long,%20android.app.PendingIntent)) [Notification countdown API](https://developer.android.com/reference/android/app/Notification.Builder#setChronometerCountDown(boolean)) [NotificationManager FSI API](https://developer.android.com/reference/android/app/NotificationManager#canUseFullScreenIntent()) [Live Updates guide](https://developer.android.com/develop/ui/views/notifications/live-update)

For a new 2026 phone-only Compose app, **minSdk 26** is a pragmatic recommendation: notification channels are universal in the supported set and legacy pre-channel behavior disappears. This is a product/support choice, not a Play requirement. API 36 Live Updates must remain progressive enhancement regardless of minSdk.

## Facts not fully verifiable from primary sources

* No primary source promises that Google Play will classify this exact “daily priority budget” product as a qualifying timer; the policy lists timer apps, but approval is case-specific.
* Official docs describe API behavior but do not provide a current, exhaustive OEM-by-OEM list of alarm-killing deviations. Device-matrix testing is required.
* Official Live Updates examples do not expressly approve or reject a general-purpose countdown/budget timer, so promotion eligibility may vary by platform/OEM interpretation.
* Primary docs do not guarantee exact-to-the-millisecond delivery; “exact” remains subject to platform dispatch, hardware, force-stop, permissions, and user/OEM controls.
